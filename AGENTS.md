# Kick Fullscreen Chat — Agent Context

Browser userscript that adds a Twitch-style side-by-side fullscreen-with-chat mode to Kick.com.

## Project Overview

**Type:** Single-file JavaScript userscript  
**Primary file:** `kick-fullscreen-chat.user.js`  
**Install docs:** `INSTALL.md`  
**Target:** Any userscript manager (Tampermonkey, Violentmonkey, Greasemonkey, ScriptCat, or other) on any browser; developed and tested on Safari + Userscripts  
**Git:** `git@github.com:jakubn11/kick-fullscreen-chat.git` (default branch: `main`).

## Commands

There is no package manager, build step, linter, or automated test suite configured.

Useful local checks:

```bash
sed -n '1,80p' kick-fullscreen-chat.user.js
wc -l kick-fullscreen-chat.user.js INSTALL.md
```

Manual testing is required in a browser with a userscript manager installed:

1. Install the userscript via your manager (e.g. drag the `.user.js` file into Tampermonkey, Violentmonkey, Greasemonkey, ScriptCat, or other, or copy it into the folder configured in the Userscripts extension on Safari).
2. Open a Kick channel page.
3. Click the player's fullscreen button.
4. Verify the **Chat** button appears top-right.
5. Click it — video should shrink, chat should dock to the right.
6. Click Kick's native **Hide chat** inside the chat panel (the icon button in the chat header, ~12px in from its left edge) — split layout should tear down and the **Chat** button should reappear, on the **first** click. Test it from both starting states: with Kick's chat visible in the windowed page before you go fullscreen, and with it hidden (so the script has to sync Kick's state on open). Both must close in one click — a second click being needed means the toggle button is no longer being recognised, see the `data-chat` notes below.
7. Click **Chat** again — chat should reappear in the split layout (not stay empty).
8. Change stream quality / seek / "Go to live" with side chat open — layout should tear down and the **Chat** button should stay disabled until the new stream is playing.
9. With chat open, drag the divider between the video and chat — chat width should follow the pointer, clamped between ~260px and ~640px (and never past 60% of the screen). The video area should re-fit live. Width should persist when you close and re-open chat **and across a page reload**. Drag the divider *well past* the minimum (below ~180px from the docked edge) — the chat slot should dim (the divider itself stays neutral). Releasing while armed closes the side chat; pulling back above the threshold should un-arm (slot returns to normal) and a normal release commits the clamped width instead.
10. With chat open, click the layout-mode toggle (top-right) — chat should switch to overlay (floating semi-transparent over full-width video) and back to side-by-side. The button should look "pressed" while overlay mode is on.
11. Click the info toggle (top-right) — the streamer-info overlay should hide / show; the toggle's icon dims when hidden.
12. Open the settings gear and enable **Dock chat on left** — the chat panel and divider should jump to the left edge, the video/controls should shift right to clear it, and the stream-info overlay should sit to the right of the chat. Dragging the divider should still resize correctly. Toggle overlay mode and confirm the floating chat sits on the left without covering the bottom controls.
13. Reload the page and re-enter fullscreen — all settings (width, dock side, opacity, hide delay, toggles) should be restored. Open settings and click **Reset settings** — everything should return to defaults and stay reset after another reload. With the panel still open, click a switch (e.g. **Dock chat on left**) and then press Space — the video should play/pause and the switch must **not** toggle back; click a slider and press the arrow keys — the video should seek rather than the slider moving. Repeat both after switching apps and back. Tab through the panel and activate a control with Space/Enter — focus must stay put so keyboard navigation still works. Then shrink the usable height — a 720p display, or browser zoom at 125% — and re-open the panel: it must cap at 76vh and **scroll** to **Reset settings** rather than running off the bottom edge, with the thin family scrollbar rather than the platform default. Re-check this after adding any settings row.
14. Park the mouse over the top-right control cluster and wait for it to fade out, then switch to another app and click back into the browser window (macOS) — the activating click must reach the player (play/pause) and must **not** open the settings panel or toggle a control. Same check without app-switching: leave the pointer over the gear until the controls fade, then jiggle and immediately click — the click should go to the player. Moving to the gear normally (>200ms of travel) must still open settings on the first click.
15. Repeat the app-switch check **without letting the controls fade** — park the pointer on the gear, switch away and back within the hide delay (or turn **Auto-hide controls** off first) so the cluster is still fully visible on return. The activating click must be swallowed: no settings panel, no toggled control. Do the same with the panel already open and the cursor parked on a switch or a slider — the setting must not change. Then press Space right after switching back — the video should play/pause and nothing in the cluster may fire. A second, deliberate click a moment later must work normally.
16. Now the flavour the timed guard can't see (0.21.6): park the pointer on the gear, then come back **without clicking** — Cmd-Tab, click the browser's dock icon, or swipe back to the fullscreen Space — wait two or three seconds so the 350ms guard is long gone, and click *without moving the mouse first*. The panel must not open. Nudge the mouse a pixel and click again: it must open. Repeat with the pointer parked on a switch inside an open panel, and on the **Chat** button. Then confirm the normal path is untouched — return from an app switch, move the mouse to the gear, click: first click opens it.
17. Because the refocus guard is defending against a race, **repeat steps 15 and 16 about ten times** and in both flavours — an app/window switch (`window` `blur`/`focus`, visibility stays `visible`) and a tab switch or minimise (`visibilitychange`) — before believing it. A single clean pass proves nothing: up to 0.21.4 the guard worked on most attempts and failed only when the reactivating click beat its own focus event to the page. Also Tab to the gear, activate it with Enter (keyboard activations keep focus by design), switch away and back, and press Space — the video must play/pause and the panel must not toggle.
18. Compare the chat's action bar (channel points / Kicks / gear / green **Chat**) docked against windowed, at the 260px minimum width and with a five-digit points value. It must read identically: full-size 16px icons, the points value **inside** its own button, and even gaps. Don't eyeball this from screenshots — the two are at different scales. Measure both, e.g. `getBoundingClientRect()` on `[data-testid="channel-points-button"] svg` and on `[data-testid="channel-points-value"]`. Expect 16px icons, 24px from the points value to the Kicks icon, 8px between the buttons, and 8px gear-to-send in both states; only the elastic Kicks-button-to-gear space should differ, since it just absorbs whatever room is left.
19. Enable a **second** copy of the script (a duplicate entry in the same manager, or a second manager) and reload. The console must show one `[KickFullscreenChat] … is standing down` warning, `<html>` must carry a single `data-kfc-running`, and fullscreen must behave exactly as with one copy — in particular, open the settings panel and move the mouse around for a few seconds: it must stay open. Without the guard the panel flickers open/closed on every mousemove and idle tick, because each instance rewrites `kfc-settings-open` from its own `settingsOpen`.
20. With the sibling **kick-quality-saver** also installed, enter and leave fullscreen half a dozen times on a live channel, letting the quality pass run each time. The settings panel must never open by itself. Then check the other direction: quality-saver must still find Kick's own gear and apply the saved quality — this script's controls are invisible to it now, so a regression there looks like the quality silently not applying rather than like a flicker. To catch a recurrence early, instrument the class rather than watching for it: wrap `DOMTokenList.prototype.toggle` and log `new Error().stack` whenever the token is `kfc-settings-open`. A MutationObserver is no good here — its callback is a microtask, so the stack no longer contains the code that wrote the class.
21. With side chat open, pause the stream (Space, or Kick's own button) and click once on the video (not on the controls, not on the chat) — it must resume. Click again while it plays: **nothing** must happen, and the cursor over the video must be the plain arrow while playing and the pointing hand while paused, without needing a mouse move to catch up. Then double-click the video: fullscreen must exit. The cursor must stay `ew-resize` over the divider throughout. Then stop moving the mouse and let everything fade (set the hide delay to its 2s minimum to make this quick, and leave a busy chat running): the timeline and the control cluster go, and the **chat must stay fully readable** — a chat that blanks to black a beat later means the controls-fade lookup has re-targeted our own slot (`[KickFullscreenChat] controls-layer lookup landed on our own UI` with debug on). Check the exclusions too — with the stream paused, a click on the top-right control cluster, on an open settings panel, on the divider, on the stream-info overlay, on Kick's own controls row and on the chat panel must none of them resume it. Finally force a buffer with the side chat up (DevTools → Network → Offline for a second): Kick's loading spinner must sit in the middle of the **video area**, not the middle of the screen — the gap between the two is half the chat width, and it grows as you widen the chat.
22. Exit fullscreen — DOM should be restored to its original state, chat back in its original location, and no leftover divider / control nodes. Check the toast too (0.21.11): force one first — e.g. break `CHAT_SELECTORS` so `enableSideChat` can't find the chat and shows "chat panel not found" — then exit fullscreen and confirm `document.getElementById('kfc-toast')` is `null`. It is invisible at rest, so a leak here shows up only as a query, never by eye.
23. Set a wide chat width (drag the divider to ~640px or click **Max**) on a full-size window, then reload Kick in a **narrow** window — one under about 1070px, so 60vw is below the saved width — change any unrelated setting, and reload again on the full-size window. The width must still be what you set (0.21.11). Before that fix the load-time clamp cut it down and the next settings write saved the cut-down value, so the width was gone for good.
24. Check the browser developer console for `[KickFullscreenChat]` log lines if something doesn't work.

## Userscript Metadata

The userscript header controls permissions and host access. Keep it valid across all common userscript managers (Tampermonkey, Violentmonkey, Greasemonkey, ScriptCat, or other):

- `@match` should remain scoped to `https://kick.com/*` unless the target changes.
- `@grant none` — this userscript does not need any GM_* APIs. Do not add grants unless a feature actually requires one.
- `@updateURL` / `@downloadURL` point at the `main` branch on GitHub. If the repo or branch moves, update both.
- Bump `@version` when changing user-facing behavior or DOM logic. The `VERSION` constant near the top of the IIFE must be bumped to the **same** string in the same commit — it is what `KickFullscreenChat.version` reports, so a stale constant makes the console API name a build the user isn't running.

Do not add `Co-Authored-By:` trailers to git commits.

## Implementation Map

`kick-fullscreen-chat.user.js` is organized into these areas:

- Userscript metadata header
- Single-instance guard (0.21.8) — the first thing inside the IIFE, before any state or listener exists. Marks `<html>` with `data-kfc-running="<version>"`; a later copy sees the marker, `console.warn`s naming both versions, and `return`s. Two copies on one page do not coexist — every node the script owns has a fixed id, so the second instance's `ensureButton()` adopts the *first* instance's `#kfc-toggle-wrap` and both then write their own state onto it. `syncControlState()` runs on every idle tick and mousemove and rewrites `kfc-settings-open` from *its* `settingsOpen`, so an open settings panel flickers: the copy that never saw the gear click closes it, the copy that did re-opens it on the next pointer movement. The marker is a DOM attribute, not a `window` property, because managers disagree on whether userscripts share a JS context (`@grant none` runs in the page context, sandboxed grants don't) but they always share the DOM. First instance wins, deterministically
- Constants — element IDs (`BTN_ID`, `WRAP_ID`, `STYLE_ID`), `CHAT_WIDTH`, the inlined Kick button SVG (`BTN_SVG`), and Kick's button class string (`BTN_CLASS`)
- Fragile DOM selectors — `VIDEO_WRAPPER_SELECTORS`, `CHAT_SELECTORS`
- Chat discovery — `pick()`, `findChatByInput()`, `findChat()`
- Kick state helpers — `setKickDataChat()` toggles the `data-chat` attribute Kick uses to drive chat visibility via Tailwind `group-data-[chat=false]/main` rules
- Style injection — `injectStyles()` adds the `[data-kfc-video-root]` shrink rules, chat-slot positioning, and button wrapper positioning
- Split-layout state — `savedChatParent`, `savedChatNextSibling`, `chatSlot`, `videoRoots`, `videoOverlays`, `videoFrames`, `markedVideos`, `videoRootHost`, `videoRootObserver`, `active`, `suppressObserver`
- Player-layer marking — `refreshVideoRoots()` marks fsEl's full-coverage children as `[data-kfc-video-root]` (the shrink + `translateZ` containing block), `refreshVideoFrames()` marks the video's ancestor chain inside them as `[data-kfc-video-frame]` and the videos themselves as `[data-kfc-video-el]`, and `refreshVideoOverlays()` (0.21.10) marks what the first one deliberately leaves out: fsEl children that cover the fullscreen but carry **no controls** — Kick's transient loading / blur overlays — as `[data-kfc-video-overlay]`. Those get width and `--kfc-video-shift` **only**: no height, no `overflow: hidden`, no restacking, because 0.9.7 gave them the full root treatment and they became transformed hit targets above the timeline. Without any sizing at all they keep the viewport's width while the player is shrunk, which is what put Kick's buffering spinner at the centre of the *screen* instead of the centre of the video. `clearVideoRoots()` unmarks all four
- Reload-resilience state — `videoReloading`, `videoReadyTimer`, `fullscreenVideoEl`, `videoSwapObserver`, `pendingVideoEl`
- Capture-phase teardown handlers — `onDocClickCapture` (quality / seekbar / go-live), `onDocPointerDownCapture` (seekbar), `onDocChatToggleClickCapture` (Kick's chat-toggle button anywhere on the page — detected by `CHAT_TOGGLE_RE` text/aria/title match or `looksLikeChatToggleBtn` SVG-path-signature match). **There are two toggle buttons, not one**, and both sit in the DOM in both states (the inactive one is 0×0 or parked off-screen, never removed): the floating **Show chat** (`KICK_SHOW_CHAT_PATH_SIG`, in `div.absolute.top-7` over the player) and **Hide chat** (`KICK_HIDE_CHAT_PATH_SIG`, in the chat panel's header, 12px in from its left edge). `looksLikeChatToggleBtn` matches either, because for click *detection* the direction is irrelevant. `findKickShowChatBtn()` matches the show direction **only** — by icon, and by the narrower `SHOW_CHAT_RE` rather than `CHAT_TOGGLE_RE` — because it *clicks* what it finds; taking the first icon match in document order there would drive Kick's state the wrong way
- Player gestures — `onFsClick` (click → **resume only**, 0.21.10) and `onFsDblClick` (double-click → exit fullscreen, 0.9.9), both bound to `fsEl` in `enableSideChat()` and unbound in `disableSideChat()`. **Kick handles both gestures on the `<video>` element**, and the side layout sets `pointer-events: none` on the marked video (`video[data-kfc-video-el]`) so clicks fall through to Kick's controls underneath — which is what keeps the player clickable after a background refresh, and which also means neither of Kick's own handlers ever sees a click while side chat is active. So the script has to provide them; if the video's `pointer-events` rule is ever revisited, these two are what depend on it. Both go through the shared `isVideoSurfaceTarget(target)` gate (`isVideoSurfaceClick(e)` wraps it): not one of ours (`isKfcOwnedNode` — chat slot, control wrap, settings panel, info overlay, divider, toast), not on `button, [role="button"], [role="slider"], a, input, textarea, select, [contenteditable]`, and not on the seekbar (`isSeekbarClick` — that click belongs to the teardown path). `onFsClick` additionally requires `e.isTrusted && e.detail >= 1`, the same rule `wireControlButton` applies (0.21.9), so a sibling userscript clicking its way around the player can't drive playback. **The click is deliberately one-way** (`canResumeByClick()`): it resumes a paused stream and does nothing at all to a playing one. Kick's own handler toggles, but a pause is the outcome nobody aims for — a mis-aimed click on the player, or the click that re-activates the window — and one-way also means the `dblclick` that exits fullscreen has no first-click toggle to undo. Don't "restore" the toggle without being asked. **The cursor is part of this and follows the same two conditions**: Kick's `cursor: pointer` lives on the `<video>`, which never gets hit while it is click-through, and an inherited cursor loses to an explicit one on whatever element takes the hit (Kick stacks its own full-size layers over the video), so a CSS rule on the marked layers is not enough — an earlier attempt at one was dropped precisely because it also painted a hand while the stream was playing, i.e. while a click does nothing. `applySurfaceCursor(target)` runs from `onFsMouseMove` on trusted moves while `active`, remembers the hovered node in `hoverTarget`, and `refreshSurfaceCursor()` puts an inline `cursor: pointer !important` on it only while `isVideoSurfaceTarget` **and** `canResumeByClick()` hold; `videoEl`'s `play`/`pause` listeners re-run it so a state change under a stationary pointer is picked up. `resetSurfaceCursor()` on teardown. Cursor and click cannot disagree by construction. Note `onFsMouseMove()` is also called with no event from a dozen places — those must not strip the cursor from an element the pointer is still on, hence the `else if (e)`
- Layout toggle — `enableSideChat()`, `disableSideChat()`
- Buttons / controls — `ensureButton()` builds the top-right control cluster (`#kfc-toggle-wrap`, a flex row): the info-overlay toggle (`#kfc-info-btn`), the layout-mode toggle (`#kfc-mode-btn`), and the **Chat** button (`#kfc-toggle-btn`). `removeButton()` (which also removes `#kfc-toast` and clears its pending fade timer, 0.21.11 — `showToast()` parents the toast to whatever is fullscreen at the time, and it was the one node teardown left stranded inside Kick's React-managed player subtree), `updateBtnLabel()` (Chat-button label + disabled state only; per-button show/hide is CSS via `.kfc-active` scoping), `syncControlState()` (reflects the saved prefs onto fsEl classes + button aria-labels), `toggleOverlayMode()`, `toggleInfoOverlay()`. All four buttons are wired through the shared `wireControlButton(btn, onActivate)` helper, which swallows the click from the player underneath, drops focus, applies the refocus guard, then runs the action. **Focus:** `blur()` runs on `pointerdown` unconditionally (deferred a task — mousedown's default action applies the focus *after* the handler) and again on `click` for **pointer** clicks (`if (e.detail)`, so keyboard activations keep focus). Blurring from `click` alone was not enough: a press whose click is swallowed or retargeted never reaches the button, leaving it focused, and when the window regains focus (e.g. switching apps on macOS) a later Space/Enter meant for the player re-triggers it, opening the settings panel or toggling a control "randomly". **Refocus guard:** `controlsAcceptActivation({ pointer, consume })` has two independent halves, and both are needed. **The untimed half (0.21.6):** `pointerParked` is set in `onWindowLeft` and cleared only by a trusted `pointermove` (window, capture) or a non-mouse `pointerdown`; while it is set, a *pointer* activation is rejected. Nothing the user does in another app moves the pointer over this page, so an activation arriving with the pointer still where it was left was aimed at whatever was last under it, not at the control the return parked it on. This is a state gate, not a window — there is no clock to lose a race against. It consumes itself on the rejected activation (`consume`), so the deliberate retry works; `consume` is **false** for the panel's `pointerdown` check, because disarming on the press would wave the click 50ms behind it straight through. Keyboard activations pass `pointer: false` (`detail === 0`) — they have no pointer to have parked, and the `onWindowLeft` blur covers them. **The timed half:** every activation is rejected while fewer than `CONTROLS_FOCUS_GUARD_MS` (350ms) have passed since `focusRegainedAt`, *or* while `reactivationPending` is latched and the guard has not been seen to expire. The bare-`focusRegainedAt` clause is a second source for the case where focus left for an iframe or browser chrome without the top-level window seeing a `blur`, leaving the latch unarmed for the whole trip. The click that re-activates a backgrounded window/tab is delivered straight into whatever sits under the parked cursor; `.kfc-unarmed` (below) only gates the case where the cluster had faded away, so a switch shorter than `idleDelayMs` — or **Auto-hide controls** off — leaves it fully armed with nothing to gate. The refocus click arrives within a frame; a deliberate click takes far longer to aim. **Latch on the way out, never on the way in** (0.21.5): `reactivationPending` is set from `window` `blur` and the hidden branch of `visibilitychange`, which happen before anything else in the sequence, and `focusRegainedAt` is zeroed there. 0.21.3 instead *armed* the guard from the `window` `focus` / visible-branch handlers, so the guard did not exist until the return event had been delivered — and the focus change and the mouse event do not share a delivery path, so on the frames where the click won that race the guard was unarmed and the panel opened anyway. That is why the bug survived 0.21.3 as an occasional one. `focusRegainedAt` is stamped by the return event if it arrives first, and otherwise by `controlsAcceptActivation()` itself off `document.hasFocus()` (an activation proves the window is active again), so the guard is the same length whatever the ordering, and it still expires if no return event ever arrives. **The timed half alone is not enough, and 0.21.6 is why:** it can only cover a return and a click that are one gesture. Focus frequently comes back on its own first — Cmd-Tab, the dock icon, swiping back to a fullscreen Space, or an activating click that landed on the video — and the click the user meant follows a second or two later with the pointer still parked. By then the 350ms have expired and the `>= CONTROLS_FOCUS_GUARD_MS` branch does not merely fail to block, it *returns true*. Do not "simplify" the two halves back into one; a longer `CONTROLS_FOCUS_GUARD_MS` is not a substitute, because the delay here is however long the user takes. The latch is cleared only by an activation that outlives the guard, so it can't stick. Note `window` `blur` also fires for browser chrome (omnibox, devtools) and, in some browsers, for focus entering an iframe: the cost is one swallowed control click on return, which is what 0.21.3 already did via the focus event. **Anything that must not fire on a refocus click goes through this function** — do not add a second timing window. `#kfc-settings-panel` applies the same guard itself, in **capture** phase on both `pointerdown` and `click` (a slider's thumb jumps on the press, not the click), so a parked cursor over a switch can't flip it on return. `onWindowLeft` also `blur()`s any of our controls that still holds focus, because the browser restores that focus on return and a restored control is armed for the reflexive Space/Enter — keyboard activations keep focus by design, so leaving is the only point where dropping it costs Tab users nothing. Ported from kick-quality-saver's `LAUNCHER_FOCUS_GUARD_MS`, which arms on the way in and so still has the race this fixed. **Untrusted clicks are rejected outright (0.21.9), before any of the above.** A `MouseEvent` dispatched by script carries `detail === 0`, which every branch here reads as a *keyboard* activation and therefore waves past the parked-pointer half — so a sibling userscript clicking its way around the player fires our controls. That is not hypothetical: kick-quality-saver's `findSettingsGear()` matched this script's gear via `button[aria-label*="settings" i]:not([aria-label*="chat" i])` and `clickQuietly`'d it up to three times a pass, which is the real cause of the "panel flickers open and shut on entering fullscreen" bug that 0.21.8 misattributed to a duplicate install. A keyboard Enter/Space produces a **trusted** click, so this costs Tab users nothing, and nothing in this script clicks its own controls. **Do not extend the `isTrusted` rejection into `#kfc-settings-panel`'s capture guard**: clicking a switch's label row reaches the checkbox as a browser-forwarded click, and gating that risks making the label text dead. **The controls' aria-labels are part of the fix, not cosmetic** — they must contain "chat" so sibling scripts' `settings`-but-not-`chat` gear heuristics skip them, and "chat" must not directly follow the leading verb, because `CHAT_TOGGLE_RE` / `SHOW_CHAT_RE` match `open|close|…` immediately followed by "chat" and "Open chat settings" would make this script mistake its own gear for Kick's chat toggle. "Open/Close fullscreen chat settings" satisfies both. **The same blur rule applies to every control inside `#kfc-settings-panel`** (width chips, switches, sliders, Reset settings, the ✕) via the shared `blurOnPointerActivate(el, focusTarget?)` helper — the panel floats over the player, so a control that keeps focus swallows Space/Enter (play/pause) and the arrow keys (seek). For switches the helper is bound to the **label**, not the checkbox: clicking the row's text reaches the input as a synthetic `detail === 0` click, so binding to the input alone would silently skip the blur. Any new panel control must go through this helper
- UI prefs — `chatWidth` (px), `chatSide` (`'right'`/`'left'`), `overlayMode` (bool, derived from `openChatAsOverlay` on each open — not persisted), `infoHidden` (bool), `infoBgOpacity` (0–90%), `overlayOpacity`, `autoHideOverlayChat`, `autoHideControls`, `openChatAsOverlay`, `restoreChatOnFullscreen`, `idleDelayMs`, `debugOn` (verbose logging, toggled via `KickFullscreenChat.debug()`). **Persisted** to a single `localStorage` key (`kfc-settings`) via `saveSettings()` / `persistSettings()` (debounced 300ms) and restored at startup by `loadSettings()`. **`loadSettings()` deliberately does *not* run `chatWidth` through `clampChatWidth()`** (0.21.11): that helper's third term is 60% of the *current* viewport, and at `document-idle` the only viewport there is is the windowed one — the wrong one to measure a fullscreen layout against, and never the narrower of the two, so the term could only ever clamp too hard. It was also lossy rather than cosmetic, because the loaded value is what the next `persistSettings()` writes back, so opening Kick once in a narrow window permanently shrank a width set on a wide display. Load applies the static `CHAT_WIDTH_MIN`/`CHAT_WIDTH_MAX` bounds only, guarded by `Number.isFinite` so NaN-producing storage can't reach `--kfc-chat-width`; the viewport term stays where a live viewport actually exists, in `setChatWidth()`. Don't "tidy" the two back into one call. Persist on every settings mutation; `resetSessionSettings()` restores defaults and re-saves.
- Chat dock side — `chatSide` (`'right'` default). `syncControlState()` toggles `html.kfc-chat-left` (flips `.kfc-chat-slot` and `#kfc-resize-handle` to the left edge via CSS) and sets three `documentElement` offset vars that all reference `--kfc-chat-width` so they track live resize: `--kfc-video-shift` (side mode — `translateX` the shrunken player right of the chat), `--kfc-control-shift` (overlay mode — `margin-left` the full-width controls row clear of the floating chat), `--kfc-info-offset` (push the top-left info overlay right of the chat). All are `0`/removed when docked right. `onResizePointerMove` measures from the left edge when docked left.
- Chat-width resize — `applyChatWidth()` (writes `--kfc-chat-width` on `documentElement`), `clampChatWidth(px, viewportWidth?)` (260–640px, ≤60vw — applied on drags, preset chips and reset, but **not** at load; see UI prefs above), `mountResizeHandle()` / `removeResizeHandle()`, and the pointer drag handlers (`onResizePointerDown/Move/Up`) on `#kfc-resize-handle`. The width is a CSS variable referenced by both the chat-slot width and the video-shrink `calc()`. **Smoothness:** `onResizePointerMove` only stores the pointer X and schedules one `requestAnimationFrame` (`resizeMoveFrame`); `applyResizeFromPointer` does the actual width update at most once per frame, so a high-polling-rate mouse / high-refresh display can't trigger several full chat-subtree reflows per frame. The viewport width is snapshotted at pointer-down (`resizeViewportWidth`) and threaded through `setChatWidth`/`clampChatWidth` so the per-frame update never reads `window.innerWidth` after the move has dirtied layout (which would force a synchronous reflow). `scheduleLiveResizeLayout()` early-returns while `resizing`, deferring the heavy player relayout (`refreshVideoRoots` + synthetic window `resize`) to the `nudgePlayerResize()` on release; the video box still tracks the divider live via pure CSS. **Drag-to-close gesture:** while the user drags the divider, `applyResizeFromPointer` compares the *raw* (unclamped) pointer width against `CHAT_WIDTH_CLOSE_THRESHOLD` (180px). When raw width drops below it, `resizePendingClose` is armed — the chat slot gains a `.kfc-pending-close` class (dims to opacity 0.35); the divider itself is left untinted (kept as the existing neutral/green hover treatment) since the slot dim alone reads clearly enough. On `pointerup` (not `pointercancel`) with the flag set, `onResizePointerUp` calls `disableSideChat(fsEl)` to tear the side layout down before the usual `nudgePlayerResize`; otherwise the flag and class are cleared and the drag commits a normal clamped width. Double-click on the divider still resets width to `CHAT_WIDTH` regardless.

- Idle auto-hide — `startIdleTracking()`, `stopIdleTracking()`, `onFsMouseMove()`, `setIdle()`, `IDLE_MS` — fades both `#kfc-toggle-wrap` (the whole control cluster) and `#kfc-info-overlay`. **The cluster must not be clickable while it is invisible.** `.kfc-idle` sets `opacity: 0` *and* `pointer-events: none`, but `pointer-events` is discrete — it reverts the instant the class is dropped, while `opacity` still has the full `.2s` fade ahead of it, and an `opacity: 0` element is hit-tested normally. Without a guard the whole cluster is clickable from the first frame of the fade-in, and a click arriving then hits whichever control is under the cursor instead of the player (typically the gear, mid-cluster → "the settings panel opens randomly"; the usual trigger is the macOS window-activating click, whose pointer movement un-idles the controls just before the click lands). `setIdle()` therefore adds `.kfc-unarmed` (`pointer-events: none` on the wrap, re-enabled for non-`button` children so panels stay live) on the idle→visible transition **only**, and clears it via `controlsArmTimer` after `CONTROLS_FADE_MS`. Two invariants: `CONTROLS_FADE_MS` must match the wrap's opacity transition duration, and only the transition arms — arming on every `mousemove` would leave the buttons permanently unclickable while the pointer moves. This is the hit-testing part of the "random settings panel" bug; the `blur()`-on-pointer rule and the two halves of `controlsAcceptActivation()` — the `CONTROLS_FOCUS_GUARD_MS` timed guard and the `pointerParked` state gate (see the controls entry above) — are the rest, and every one of them is needed. The fade guard is inert when the cluster never faded (short app switch, or **Auto-hide controls** off), which is what the refocus guard covers; the timed guard in turn is inert when focus returns on its own and the click comes seconds later, which is what the parked-pointer gate covers. Note the refocus guard only actually held once it was latched from `blur` rather than armed from `focus` (0.21.5): before that it could be bypassed by a reactivating click that beat its own focus event to the page. Even then it only covered returns where coming back and clicking were one gesture; the parked-pointer state gate (0.21.6) covers the returns where focus comes back on its own and the click follows seconds later, which is why the bug outlived four fixes. **None of these guards is about a click the user made at all, and one flavour of "the panel opens by itself" isn't:** a sibling userscript dispatching clicks at what it thinks is Kick's player gear reaches ours with `isTrusted === false`, which 0.21.9 rejects up front (see the controls entry). Before attributing a fresh report to any guard above, instrument `DOMTokenList.prototype.toggle` for `kfc-settings-open` and read the stack — that is what identified this one, after 0.21.8 had reasoned its way to the wrong culprit from correct premises

- Popover portal — `startPopoverPortal()`, `stopPopoverPortal()`, `adoptPopover()`, `reconcilePopoverClones()`, `removePopoverClone()`; while side chat is active, *clones* body-portaled popovers (emote-name tooltips etc.) into the fullscreen element so the Fullscreen API displays them. The mutation handler coalesces bursts of message activity into one `chatSlot.textContent` scan per frame using `chatErrorCheckScheduled` (a stored `requestAnimationFrame` id, cancelled by `stopChatErrorWatcher`); when the fallback is seen, the watcher logs, shows a `showToast` ("Kick chat errored. Click Chat to reopen."), disconnects itself, and calls `disableSideChat(fsEl)` to put the chat node back where Kick expects it so the user can re-dock without a full page reload. `chatErrorRecovering` guards re-entrance during the teardown so textContent changes from the move itself don't re-trigger the handler.

The central state that drives the split layout is:

```js

let videoReloading = false;     // player is reloading; Chat button must stay disabled
let savedChatParent = null;     // where to put chat back on teardown
let savedChatNextSibling = null;
let chatSlot = null;            // .kfc-chat-slot we created
let videoRoots = [];            // fsEl children currently tagged data-kfc-video-root
let videoRootHost = null;       // the fsEl those markers are on
let videoRootObserver = null;   // MutationObserver re-marking after Kick swaps layers
```

The core idea: when the user activates the side chat, the chat node is **moved** into a new `.kfc-chat-slot` (`position: fixed` on the right) inside the fullscreen element. Kick's player nodes stay parented to `fsEl` — they are not moved. Instead, the script tags the full-coverage direct children of `fsEl` with `data-kfc-video-root`, and CSS shrinks them to `calc(100% - 340px)` while `transform: translateZ(0)` makes each marked element a containing block for its `position: fixed/absolute` descendants. On tear-down, the chat node is restored to its original parent (and original `nextSibling` insertion point if still present); the markers and chat slot are removed.

This in-place marker design replaced the older `.kfc-video-slot` wrapper (0.9.1 and earlier). Wrapping `fsEl`'s children caused React to throw on long-running background refreshes — its reconciler would try to remove a node from `fsEl` and find it inside our wrapper instead, and Kick's error boundary navigated to its 404 page.

## External APIs

None. This userscript does not perform any network requests and does not depend on third-party services. All work is DOM manipulation inside the Kick page.

## DOM And Routing Notes

Kick is a single-page app and may change class names. The fragile selectors live near the top of the userscript:

- `VIDEO_WRAPPER_SELECTORS` — candidates for the fullscreened player container (`#injected-channel-player`, `[data-testid="player"]`, etc.)
- `CHAT_SELECTORS` — candidates for the chat panel (`#chatroom`, `[data-testid="chatroom"]`, etc.)
- `STREAMER_INFO_SELECTORS` — candidates for Kick's channel-info card cloned into the top-left fullscreen overlay (`[data-testid="streamer-info"]`, `[data-testid="channel-info"]`, `#channel-header`, etc.). When Kick renames the card, add new fallback selectors at the end rather than replacing working ones.
- `VIEWER_COUNT_SELECTORS` / `VIEWER_COUNT_RE` — the viewer-count badge, cloned as a separate child because Kick renders it outside the compact streamer card. Selectors are tried first; `VIEWER_COUNT_RE` is the content-based fallback that `findViewerCountSource()` uses to pick the smallest element whose text looks like "770 Viewers". When adding a localised token to that pattern, note the trailing guard is `(?!\p{L})` under the `/u` flag and **not** `\b` — outside `/u`, JS `\w` is ASCII-only, so a `\b` after a token ending in a non-ASCII letter silently never matches (see 0.20.3). Verify any new token against a real string before trusting it.

When fixing Kick DOM breakage, prefer adding fallback selectors rather than replacing working selectors. `findChat()` already falls back to walking up from a chat input/textarea whose placeholder matches `chat|message|send a message` — extend that heuristic before resorting to brittle class-name matching.

`data-chat` is the attribute Kick uses on a player ancestor to drive chat visibility through Tailwind variants like `group-data-[chat=false]/main:block`. The script:

1. Sets `data-chat="true"` when entering the split layout, so chat is not hidden by Kick's own CSS once it has been moved into our chat slot.
2. Observes `data-chat` mutations and tears down the split layout when Kick sets it to `"false"` (e.g. when the user clicks Kick's native **Hide chat** button).
3. Uses a `suppressObserver` flag so our own writes do not immediately re-trigger the observer.

**The `data-chat` observer is not sufficient on its own, and `onDocChatToggleClickCapture` is not just an optimisation.** Because step 1 forces the attribute to `"true"`, Kick's React can be left believing chat is hidden while the attribute says shown — via the `enableSyncUntil` reconcile guard, or a sync click that didn't land. From that state the user's first click on Kick's hide button drives React *towards* shown, so `data-chat` goes to `"true"` and the observer, which only acts on `"false"`, does nothing; the second click finally produces a `"false"`. The capture handler tears down on the click itself, whichever way the attribute moves, which is what makes it one click. That is why a stale icon signature there surfaced as "closing the chat takes two clicks" (0.21.7) rather than as an obvious break — keep it matching, and prefer adding a signature to replacing one.

Always test after selector or attribute changes:

- Entering fullscreen — **Chat** button appears
- Activating split layout — chat moves in, video shrinks
- Clicking Kick's native **Hide chat** — split layout collapses, **Chat** button reappears
- Re-activating split layout — chat content is visible (not an empty dark slot)
- Exiting fullscreen — chat returns to its original DOM location

## Layout Notes

- Kick's player nodes are **not** moved. The script tags the full-coverage direct children of `fsEl` with `data-kfc-video-root`, CSS shrinks each marked element to `width: calc(100% - var(--kfc-chat-width)) !important; max-width: same; height: 100% !important`, and the chat panel is docked as `position: fixed; top: 0; right: 0; bottom: 0; width: var(--kfc-chat-width)` so it overlays the right side of the screen.
- **Chat width is a CSS variable.** `--kfc-chat-width` (default `340px`, written on `documentElement` by `applyChatWidth()`) drives both the shrink `calc()` and the slot width. The `#kfc-resize-handle` divider updates it live during a pointer drag, clamped to 260–640px and ≤60vw. The value lives in `chatWidth` and is persisted to `localStorage` (debounced), so it survives both open/close and a page reload.
- **Overlay mode** (toggled by `#kfc-mode-btn`) overrides the video shrink back to `width: 100%` by setting `--kfc-video-width: 100%` on `documentElement`, and gives `.kfc-chat-slot` a translucent blurred background via the `.kfc-overlay` class on the slot, so the chat floats over the full-width video instead of shrinking it. Reset on teardown by `syncControlState()`; the `overlayMode` preference is retained for the next open. **Do not key this (or any control state) on a class on `fsEl`** — Kick's React strips `fsEl`'s `className` on re-render (the same reason `[data-kfc-video-root]` is re-applied by an observer), which previously reverted the controls mid-resize. Drive state from our own nodes + `documentElement` variables only.
- `looksLikeFullscreenLayer` only marks direct `fsEl` children whose `getBoundingClientRect()` covers **both** ≥70% width *and* ≥70% height (or which contain a `<video>` regardless of size). Earlier OR-based heuristics dragged tall-but-narrow popovers (quality / settings menus) into the shrink and broke their placement. **The width basis is the available video width (viewport − chat) while side chat is open, not the full viewport** (`coversFullscreen`): a controls layer that only holds the timeline (no `<video>`, so it must pass the size+controls test) is shrunk to `100% − chatWidth`, and measuring it against the full viewport would drop it below 70% once the chat is dragged wide — un-marking it, losing the `translateZ(0)` containing block, and letting Kick's `position: fixed` timeline escape across the chat. In overlay mode the basis is the full viewport (video isn't shrunk).
- Marker selectors (`[data-kfc-video-root]`, `.kfc-chat-slot`) are intentionally **not** scoped under `.kfc-active`. Kick's React periodically re-renders `fsEl` and writes its own `className`, stripping `.kfc-active`. The `data-kfc-video-root` attribute is set on Kick's own nodes, so a `MutationObserver` (`videoRootObserver`) re-applies it whenever Kick swaps a layer. `.kfc-chat-slot` is on a node we created and Kick never touches.
- **Kick's chat action bar (channel-points / gift-shop / settings / `#send-message-button`) needs one *kind* of override — releasing forced widths — but it has to be applied at every wrapper level.** Kick's left group carries `lg:w-full`, and the `lg:` breakpoint keys off the **viewport**, which stays wide in fullscreen even though the chat panel is 260–640px — so the left group claims the whole row and pushes the green send button past the slot's `overflow-x: hidden`. Setting `width: auto; flex: 0 1 auto` on it is the whole fix; the right group's own `ml-auto` then keeps the send button flush right. **Release the forced width on *every* wrapper down to the buttons, not just the outer group** — Kick nests a second `w-full` div between the channel-points button and the gift-shop's span, so the rule needs all three of `:has(> [data-testid="channel-points-button"])`, `:has(> [data-testid="gift-shop-button"])` and `:has(> * > [data-testid="gift-shop-button"])`. Missing that last one is what made the docked bar visibly differ from the windowed one through 0.21.3: the middle wrapper demands 100% of its parent, and while a windowed flex item floors at `min-width: auto`, the slot-wide `min-width: 0` above (which the message rows need) strips that floor, so the wrapper crushes the points button — its 16px icon rendered at 8.5px and the value overflowed ~10px past the button. Match wrappers a level at a time with `> * >` rather than naming the `span`, so a wrapper swap in Kick's markup doesn't silently reopen it. **`flex: none` on the icons is not the fix** — it un-squashes the icon while making the value's overflow worse (measured 17px vs 10px); release the wrapper instead. **Do not tighten padding or gaps on top of that** — an earlier version squeezed both buttons to `.375rem` padding and every gap to `.25rem`, which is what made the docked bar read as cramped against the windowed one (the channel-points value nearly touching the Kicks icon). Measured against Kick's real markup at the 260px minimum, that squeeze reclaimed 29px the row never needed; with Kick's own spacing left alone there is still ~9px spare and the send button keeps its natural width. **No spacing value here is ours** — measured against Kick's markup, the value-to-icon gap (24px), button-to-button gap (8px) and gear-to-send gap (8px) are identical docked and windowed at every chat width and points value. The outer row's gap is Kick's `lg:gap-0`, not a floor: a `.5rem` floor was tried and removed, since the right group's `ml-auto` already keeps the groups apart and the gap was charged unconditionally, costing the send button 3px at the 260px minimum with a five-digit points value. The one gap that legitimately differs from windowed is the elastic Kicks-button-to-gear space, which tracks chat width (~30px at 260px vs ~89px for a windowed sidebar) and is not a defect. Selectors go through the stable `#send-message-button` id and Kick's `data-testid`s, never Tailwind class names.
- `[data-kfc-video-root]` sets `transform: translateZ(0)` so each marked layer acts as a containing block for Kick's `position: fixed/absolute` descendants — without this, the timeline / controls anchor to the viewport and overflow across the chat panel.
- The video element inside a marked layer is forced to `width/height: 100%` with `object-fit: contain` so it fills the shrunken area without leaving black side bars.
- The toggle button wrapper (`#kfc-toggle-wrap`) fades via the `.kfc-idle` class (`opacity: 0; pointer-events: none`) after `idleDelayMs` of no real `mousemove` on the fullscreen element. Kick's own controls overlay fades on its own fixed internal timer (~`KICK_NATIVE_IDLE_MS`), which the user can't change. When the configured delay exceeds that, `startKeepAlive()` dispatches **untrusted** synthetic `mousemove`s on the player to reset Kick's timer, with the final nudge scheduled `idleDelayMs - KICK_NATIVE_IDLE_MS` in so Kick's timeline fades together with our overlay instead of sooner. `onFsMouseMove` ignores untrusted events so these nudges don't reset our own idle timer. When the configured delay is **shorter** than Kick's native timer, `setKickControlsHidden()` fades Kick's controls layer to `opacity: 0` + `pointer-events: none` (inline `!important`, **no** height/layout changes) the moment we go idle, so the timeline hides in step with our overlay. `findKickControlsLayer()` locates the cluster from the seekbar and climbs only as far as the subtree that does not contain the `<video>`, so the video layer is never faded; a childList-only observer (`kickControlsObserver`) re-applies the fade across React re-mounts during idle. **Both the search and the observer are scoped to `videoRoots`, never to `fsEl` alone** (0.21.10). The docked chat is a child of `fsEl` too, so an `fsEl`-wide seekbar search can match something inside the chat, and since the climb stops at the top-level child of `fsEl` it then returns **the chat slot itself**, which gets `opacity: 0 !important` — the "chat goes black a second after the timeline hides" bug. It needs Kick's seekbar to be missing at lookup time, which is normal during idle (Kick unmounts its hidden controls), and the delay is the reapply pass being driven by DOM churn that the chat's own message stream supplies. `fsEl` remains a last-resort scope, but candidates inside our UI are skipped (`isKfcOwnedNode`) and the climbed result is refused if it is the chat slot, one of our nodes, or an ancestor of the chat. Anything that fades or hides a node found by searching `fsEl` needs the same two filters. This is a deliberately minimal re-take on the height-based control overrides removed in 0.17.0 — opacity-only, so the timeline never shifts off the bottom.
- The streamer info overlay (`#kfc-info-overlay`) is anchored top-left of the fullscreen element and fades through the same `kfc-idle` class as the toggle button, so it appears with Kick's timeline/controls and disappears with them. It is `pointer-events: none` so clicks pass through to the player. Follow / subscribe / share / notification controls inside the cloned card are hidden via CSS so the overlay stays compact.

## Reload-Resilience Notes

When Kick's React reconciler re-mounts the player tree (quality change, seek, DVR exit, popstate), our layout can collide with the reconciliation and the page navigates to Kick's 404 error page. The script defends against this in three layers:

1. **Capture-phase teardown.** `onDocClickCapture` and `onDocPointerDownCapture` catch clicks on quality popover items, the seekbar, and "Go to live" buttons *before* Kick's onClick runs, set `videoReloading = true`, and call `disableSideChat()` synchronously so the DOM is back in Kick's expected shape before reconciliation runs.
2. **Disabled Chat button.** `updateBtnLabel()` disables the **Chat** button whenever `videoReloading` is true or the `<video>` element reports `readyState < 2`. The disabled state is enforced via `btn.disabled = true` plus Kick's own `disabled:pointer-events-none` Tailwind class on `BTN_CLASS`.
3. **Grace delay.** Even after `canplay`/`loadeddata` fires, React may still be mid-commit. `VIDEO_READY_GRACE_MS` (750ms) defers re-enabling the button. A `loadstart`/`emptied` during the grace cancels the timer and keeps the button disabled.

The video monitor (`startVideoLoadingMonitor`) attaches to whatever `<video>` is currently in `fsEl` and re-attaches on swap via a `MutationObserver`. It also synthesizes the `onVideoLoaded()` path when a *new* element is already past `readyState 2` by the time the observer wakes — but only when the element is genuinely different from the previous one (compared against `previousVideo` captured before the detach), so re-attaching to the same element doesn't clear `videoReloading` based on stale `readyState`.

`enableSideChat()` is the last line of defense: it bails when no `<video>` is present and defers (via `pendingVideoEl`) when `videoReloading` is true or `readyState < 2`.

## Security

### Rules — always follow these

- **Never use `innerHTML`, `outerHTML`, or `insertAdjacentHTML` with untrusted data.** The single existing use of `innerHTML` writes a hardcoded SVG + `<span>Chat</span>` template. Any future button content must remain hardcoded — never interpolate provider responses, DOM text, URL fragments, or user input.
- **Never use `eval`, `new Function(string)`, `setTimeout(string)`, or `setInterval(string)`.**
- **Do not introduce network requests** without explicit reason. There are currently no `fetch`, `XMLHttpRequest`, `GM_xmlhttpRequest`, or remote image loads. Adding one would require a `@connect` entry and a security review of the destination.
- **Persistence is limited to one `localStorage` key (`kfc-settings`)** holding UI preferences (see `saveSettings()` / `loadSettings()`). All reads/writes are wrapped in `try/catch` (private mode / disabled storage) and every value is validated/clamped on load. Do not store anything else, and never persist untrusted or sensitive data. No cookies.
- **Do not bypass `suppressObserver`** when mutating `data-chat` from script. Doing so will cause the observer to immediately tear down the layout we just enabled, leading to flicker or infinite loops.
- **Do not remove or weaken the `looksLikePlayer` check** in `onFullscreenChange` — it stops us from injecting the toggle into unrelated fullscreen targets.

### Checks — run mentally before every commit

- Does any new code assign untrusted data to `innerHTML` or similar? → Fix it.
- Does any new code introduce a `fetch` or other remote request? → Add `@connect`, justify the domain, and document it.
- Does any new code introduce a `localStorage` key beyond `kfc-settings`? → Reconsider; preferences belong in the existing `kfc-settings` blob, and all access must stay wrapped in `try/catch` with validation on load.
- Does any new code mutate `data-chat` without raising `suppressObserver` first? → Wrap the write.
- Does any new code use string-based dynamic execution (`eval`, etc.)? → Remove it.

### Existing security measures (do not remove or weaken)

- `looksLikePlayer` check in `onFullscreenChange` — only injects the toggle when the fullscreen target is a Kick player container.
- Hardcoded `BTN_SVG` + `<span>Chat</span>` template for the toggle button — the only `innerHTML` use in the script.
- `suppressObserver` flag around our own `data-chat` writes — prevents the `dataChatObserver` from tearing down the layout we just enabled.
- `@grant none` and zero `fetch` / `XMLHttpRequest` / image-load calls — keeps the attack surface to in-page DOM manipulation only.
- `showToast()` (instead of `alert()`) for surfacing errors — avoids stealing focus and breaking fullscreen.

- **One green accent per component.** The toggle button's single `#22c55e` accent is the icon (`#${BTN_ID} svg { fill: #22c55e }`). Never paint the surface green or add a second green element.
- **Hover is the green tint composited over the surface.** `#${BTN_ID}:hover` uses `linear-gradient(rgba(34,197,94,.1), rgba(34,197,94,.1)), #101013` so the tint sits on an opaque surface and text contrast holds — never set the transparent tint as a standalone background (the video would show through).
- **Disabled state is painted by the script.** Because the button dropped Kick's `disabled:*` classes, `#${BTN_ID}:disabled { opacity: .3; pointer-events: none }` provides it. Set `btn.disabled = true`/`false`; the CSS does the rest.
- **Icon control buttons share the button's surface.** The layout-mode toggle (`#kfc-mode-btn`), info toggle (`#kfc-info-btn`) and settings gear (`#kfc-settings-btn`) use the `.kfc-control-btn` class — the same `#101013` glass surface / border / blur / shadow as the Chat button, but square and icon-only, with the single green accent on the icon. Their on/off state is shown by recolouring (`#kfc-info-btn.kfc-off` dims the icon) or a pressed green tint (`#kfc-mode-btn.kfc-on`), never by inventing a new token.
- **`#kfc-toggle-wrap` is a shared surface — the sibling kick-quality-saver script mounts into it.** When both scripts are installed, that script prepends its own button as the leftmost child of the wrap, and while its settings panel is open it appends the panel as an absolutely positioned child too (right-aligned under the wrap, so the wrap's `right` transition carries it during chat resizes exactly as it carries `#kfc-settings-panel`). It also neutralises the wrap's idle fade for its own panel from its own stylesheet (`#kfc-toggle-wrap.kfc-idle:has(#kqs-settings-panel)`), mirroring the `settingsOpen` exemption in `syncControlState()`. Consequences: `ensureButton()` must keep re-appending the *same* wrap element rather than rebuilding it (a foreign child has to survive), the wrap must not assume its children are only the ones it created (`removeButton()` may drop foreign nodes on teardown, which is fine — that script rebuilds them), and renaming `#kfc-toggle-wrap` / `.kfc-idle` / `.kfc-chat-open`, or changing how the wrap moves, is a **breaking change for kick-quality-saver**. Update both scripts together. **The controls' `aria-label`s are part of that contract too (0.21.9).** kick-quality-saver hunts for Kick's player gear with `button[aria-label*="settings" i]:not([aria-label*="chat" i])`, and on fullscreen entry Kick's own gear isn't mounted yet — so a label of ours that says "settings" without "chat" gets clicked, repeatedly, and the panel flickers. Every label on a control in this wrap must contain "chat", and must not put "chat" straight after the leading verb (`CHAT_TOGGLE_RE` / `SHOW_CHAT_RE` would then read our own gear as Kick's chat toggle).
- **Per-button visibility is CSS, not a wrapper toggle.** `#kfc-toggle-wrap` stays visible (it's a flex row hosting all controls); individual buttons show/hide via `.kfc-active` scoping (Chat button only when chat is closed, mode toggle only when open). Do not hide the whole wrapper.
- **The settings panel shares kick-quality-saver's panel design.** `#kfc-settings-panel` keeps the tokens above (opaque `#101013`, `rgba(255,255,255,.1)` border, one green accent) but departs on radius — a `14px` card, `11px` groups, `8px` controls — because the nesting needs the extra step. Its structure is a header (`.kfc-settings-head`: icon mark, name, and a ✕ close button) followed by one `.kfc-settings-group` per topic. Within a group the toggle rows are wrapped in a gap-less `.kfc-settings-switches` column (mirroring the sibling panel's `.kqs-switches`) so each `.kfc-settings-check` row's own `7px` top/bottom padding is the only vertical spacing and the hairline separators sit centered between rows; a `.kfc-settings-switches:last-child` gets `margin-bottom: -7px` so a group ending in toggles has equal padding at its top and bottom edges (the sibling panel does not yet do this last part). Selected chips (`.kfc-selected`) and checked switches use a green tint plus a `0 0 0 3px` green ring. The two destructive controls — `.kfc-settings-reset` and `.kfc-settings-close` — share one look: `#fca5a5` glyph on the neutral chip surface, `rgba(239,68,68,.14)` tint and `rgba(248,113,113,.5)` border on hover. Keep them identical to each other and to the sibling panel's `.kqs-chip--danger` / `.kqs-close`. **The panel carries no `backdrop-filter` and has no backdrop element behind it** — its surface is opaque, so a blur would only add a compositing layer over the video. **It is also capped and scrollable — `max-height: 76vh; overflow-y: auto` plus the family scrollbar (8px track, `rgba(255,255,255,.13)` thumb inset by a 2px transparent border with `background-clip: padding-box`, `999px` radius) — copied verbatim from `.kqs-card`.** Uncapped, the panel just ran off the bottom of the screen: ~660px of content anchored ~76px down needs ~735px, so 720p displays and any browser zoom past ~110% clipped **Reset settings** out of reach, and kqs's panel scrolled while this one clipped *inside the same fullscreen wrap*. The 76vh is deliberately kqs's number rather than a tighter anchored `calc()` — the panel's top offset is only ~7vh at 1080p and ~10.5vh at 720p, so 76vh clears the bottom anyway and parity is worth more than the few extra rows. Flex children never shrink into the cap (`min-height: auto` keeps them at content height), so the overflow scrolls. **Every new settings row must keep this true — check the panel at 720p, not just on your own display.** Keep it visually in step with the sibling script's panel; changing one usually means changing both.
- **The resize divider is a thin neutral line.** `#kfc-resize-handle` is a near-invisible 2px line (`rgba(255,255,255,.12)`) that turns green (`#22c55e`) on hover/drag — the one accent for that component. No label, no fill, no shadow.
- **Toasts sit on the kick-\* family surface.** `#kfc-toast` surfaces internal errors (e.g. "chat panel not found") on `rgba(16,16,19,.88)` — the family's `#101013` surface at 88% — with the shared `rgba(255,255,255,.1)` border and `8px` radius, so it reads as the same material as kick-quality-saver's apply pill, kick-chat-utils' notices, and kick-vod-resume's resume toast. It carries no green accent: it is an error surface, not an interactive control.
- **The info overlay reuses Kick's own card markup.** `#kfc-info-overlay` is a *clone* of Kick's existing channel-info card; the script does not paint streamer name / title / viewer count on its own. The overlay container adds only positioning + a subtle gradient backdrop for readability — it must not introduce custom typography, badges, or colour tokens.
- **No new tooltips, menus, or popovers painted by the script.** The script's self-painted UI surface is intentionally limited to: the control cluster (Chat button + mode toggle + info toggle + settings gear), one settings panel, one chat slot, one resize divider, one toast, one info overlay (clone of Kick's card), and a per-popover clone wrapper. Do not paint new UI from scratch — clone Kick's existing nodes instead.

### Reference implementations

- `#${BTN_ID}` rules in `injectStyles()` — the toggle button, styled in the kick-\* family design language (dark surface, neutral border, blur, green icon accent)
- `.kfc-control-btn` rules — the square icon-only control buttons (mode, info and settings toggles); same surface as the Chat button
- `BTN_SVG` / `MODE_SVG` / `INFO_SVG` / `SETTINGS_SVG` constants — hardcoded icon path data for the four controls (recoloured green via CSS)
- `#kfc-toggle-wrap` — the positioned flex-row wrapper hosting the control cluster
- `#kfc-resize-handle` — the draggable video/chat divider (neutral line, green on hover/drag)
- `.kfc-chat-slot` — fixed-position chat dock; width is `var(--kfc-chat-width)`; gains a translucent backdrop via its own `.kfc-overlay` class in overlay mode
- `[data-kfc-video-root]` — in-place marker on Kick's full-coverage player layers; CSS-only shrink to the left of the chat slot (full width when `--kfc-video-width` is set to `100%` in overlay mode)
- `#kfc-info-overlay` — top-left clone of Kick's channel-info card; positioning + readability gradient only, all visible content (avatar / name / title / game / viewers) comes from Kick's own DOM
- `#kfc-toast` — neutral error toast

## Before Every Commit

Before committing any change, always:

1. **Bump `@version`** in the `kick-fullscreen-chat.user.js` metadata header using these rules:

   | Change | Bump | Example |
   |---|---|---|
   | New user-facing feature — new toggle, new layout, new keyboard shortcut | **minor** `x.+1.0` | `0.5.x → 0.6.0` |
   | Bug fix, selector tweak, refactor, internal change | **patch** `x.x.+1` | `0.5.x → 0.5.x+1` |
   | Breaking change or full rewrite | **major** `+1.0.0` | `0.x.x → 1.0.0` |

   Bump the `VERSION` constant inside the IIFE to the same value — it backs `KickFullscreenChat.version`. Verify both with:

   ```bash
   grep -n "@version\|const VERSION" kick-fullscreen-chat.user.js
   ```

2. **Update `CHANGELOG.md`** — add an entry under the new version with a short summary of what changed.
3. **Update `README.md`** if the change is user-facing: new or removed features, changed behaviour, new keyboard shortcuts, or updated troubleshooting steps. Internal refactors and bug fixes that don't change user-facing behaviour do not require a README update.
4. **Suggest a GitHub Release** after every commit if any of the following apply — say "this looks like a good point to publish a GitHub Release":
   - A security fix was made
   - A user-facing feature was added (new toggle, new layout, new keyboard shortcut)
   - A bug affecting core functionality was fixed (button missing in fullscreen, split layout broken, chat not rendering)

   Do NOT suggest a release for: docs-only changes, internal refactors, formatting, style tweaks the user won't notice.
